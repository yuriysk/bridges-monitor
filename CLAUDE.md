# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Статус

Реалізовано: довідник мостів, конфіг, модель стану руху, розклад опитування, джерела тривог і заторів, цикл опитування (`monitor.py`) з публікацією змін у лог. Ще немає: сховища (усе в пам'яті), інтерфейсу модерації, парсера тексту (LLM), офіційних текстових джерел і Telegram-бота.

## Команди

Python 3.14.8 надає pyenv (`.python-version`). `[tool.uv] python-preference = "only-system"` забороняє uv завантажувати власний інтерпретатор. Віртуальне середовище: `.venv` у корені проєкту.

```bash
uv sync                          # встановити залежності з uv.lock
uv add <пакет>                   # додати залежність (--dev для інструментів розробки)
uv run bridges-monitor traffic mapbox   # разово опитати провайдера заторів (діагностика, cli.py)
uv run bridges-monitor alerts           # разово опитати джерело тривог (діагностика)
uv run bridges-monitor run              # запустити моніторинг (Ctrl+C — зупинка); зміни стану — у лог
uv run python scripts/road_geometry.py  # перегенерувати геометрію мостів з OpenStreetMap
uv run pytest                    # тести
uv run pytest tests/test_x.py::test_name   # один тест
uv run ruff check . && uv run ruff format .
```

Ще не визначено (не вигадуй, питай у користувача): перелік офіційних та неофіційних джерел даних. Його складання потребує окремого підходу.

## Призначення

Bridges Monitor (робоча назва) — сервіс **для автомобілістів**: стан автомобільного руху київськими мостами через Дніпро під час повітряних тривог і поза ними. Чи відкритий рух, які обмеження діють і в яких напрямках, які затори. Метро на мостах відстежується додатково. Залізниця не відстежується зовсім.

## Довідник мостів

`data/bridges.toml` містить дані, `catalog.py` — модель. Зараз 6 мостів: Північний, Подільсько-Воскресенський, Метро, Патона, Дарницький, Південний.
- **Міст — один об'єкт**, навіть якщо фізично складається з кількох споруд. Північний включає міст через Десенку, Метро — Русанівський метроміст. Не дроби мости на окремі споруди: це рішення користувача.
- Види транспорту: `road` (обов'язковий на кожному мосту) і `metro`. `not_in_service` позначає те, що конструктивно є, але не працює (метро на Подільському).
- Стан ведеться для трійки (міст, вид транспорту, напрямок `to_left_bank`/`to_right_bank`).
- Назви зберігаються як словник `мова → текст`. `uk` обов'язкова, `en` перевіряє тест. Інші мови додаються без змін коду.
- Id мають вигляд `bridge-*`. Після перейменування id треба оновити `road_geometry.toml` і тести.

`data/road_geometry.toml` (`geometry.py`) — автомобільні проїзні частини мостів для джерел заторів.
- `RoadProbe` — міст в одному напрямку. Він складається з `segments` (`RoadSegment` — споруди в порядку руху) і `route_points`.
- Джерело істини — `segments[].osm_ways` (id ліній OpenStreetMap). `points` і `route_points` генерує скрипт, вручну їх не редагуй.
- `route_points` — точки на 20% першої і 80% останньої споруди, взяті саме з лінії OSM. Точки, інтерпольовані по прямій, на вигнутих мостах прив'язувалися до сусідніх доріг, і маршрут ішов в об'їзд.
- `to_left_bank` = рух на схід (Дніпро тече з півночі на південь), це перевіряє валідатор.
- В OSM продовження Подільського мосту через Десенку позначене як «будується», тому геометрія охоплює лише прогін над Дніпром.

## Архітектура стану руху

Конвеєр: джерело → `Report` → `Claim` → модерація → `compute_states()` → `diff_states()` → публікація змін.

- **`monitor.py`** — `Monitor`, цикл опитування.
  - Окремі задачі в `asyncio.TaskGroup`: джерело тривог, кожне джерело даних і перерахунок стану.
  - Коли опитувати, вирішує чиста функція `plan_poll(schedule, last_poll, now, alert)`: опитати зараз або спати до `wake_at` (кінець інтервалу або межа вікна, що настане раніше). Зміна стану тривоги будить усі цикли одразу.
  - `ingest()` проставляє модерацію за `initial_moderation()` і відкидає неофіційні повідомлення в базовій версії. Текстові повідомлення без тверджень поки пропускаються, бо парсера ще немає.
  - Стан перераховується після нових даних, зміни тривоги й раз на хвилину. Базовий стан (усе `unknown`) при старті не публікується. Збій публікації лише логується.
  - Застарілі твердження та завершені понад добу тривоги видаляються.
- **`publishing.py`** — протокол `Publisher` (`publish_changes`, `publish_alert`). Поки є лише `LogPublisher`, Telegram-канал з'явиться окремою реалізацією.

- **`sources/base.py`.** Усі джерела успадковуються від `BaseSource[T]` (вимога користувача: однаковий інтерфейс).
  - Спільне: `source_id`, `kind` (офіційне чи ні), `schedule`/`interval_at(час, тривога)`, `async fetch() -> T`, `close()`/`async with`.
  - Збої джерело повідомляє через `SourceError`.
  - `Source` — дані про мости, `fetch() -> list[Report]`. Текстові джерела віддають `Report.text`. Структуровані джерела одразу додають твердження через `make_report(claims=[...])`, а поля джерела в `Claim` заповнює база.
- **`sources/http.py`.** Спільний `HttpClient`. Помилки не містять URL-параметрів (TomTom, HERE і Mapbox передають ключ у query). Пояснення з тіла відповіді додається, але значення параметрів і заголовків із нього вирізаються.
- **`sources/alerts.py`** — `AlertSource`, `fetch() -> AlertSnapshot`.
  - Провайдери: `UkraineAlarmSource` (офіційний) і `AlertsInUaSource` (неофіційний, лише в розширеній версії). Обидва потребують `BM_ALERTS__TOKEN`.
  - Розбір відповіді ukrainealarm відтворено з документації клієнтських бібліотек, на живому API ще не перевірено.
  - **alerts.in.ua перевірено на живому API** (2026-10-06). `/v1/alerts/active.json` збігається з розбором. Київ має `location_uid` `"31"` і `location_type` `"oblast"`, а не `city`, як у документації. Ліміт — ≈ 8–10 запитів на хвилину з однієї IP-адреси. Історія тривог — `/v1/regions/31/alerts/month_ago.json` (≈ 200 тривог на місяць, ліміт 2 запити на хвилину). Знадобиться, щоб заповнити `AlertTracker` після перезапуску.
  - `AlertTracker` (`alerts.py`) перетворює результати опитувань на `AlertPeriod`.
- **`sources/traffic/`** — `TrafficSource(Source)`.
  - Провайдер реалізує лише `read(probe) -> ProbeReading | None` для мосту в одному напрямку. Опитування всіх мостів, допуск часткових збоїв і створення `Claim` бере на себе база.
  - Точкові провайдери (TomTom, HERE) опитують кожну споруду й зводять результат через `worst_reading()`. Сегмент провайдера зіставляється зі спорудою за відстанню до середини й напрямком (`shape_offset_m`), щоб не взяти зустрічну смугу.
  - Маршрутизатори (Mapbox, Google) будують один маршрут між `route_points`, тож на цикл виходить 12 запитів.
  - `closed` ставиться лише за явним повідомленням провайдера. Маршрут в об'їзд мосту (`is_detour`) означає «немає даних».
- **`schedule.py`** — `PollSchedule`.
  - Вікна «з якого часу → інтервал» за київським часом, окремо `normal` (без тривоги) і `alert`.
  - Сталий інтервал — `PollSchedule.constant()`. Конструктор джерела приймає й `timedelta`.
  - Для заторів діє `Settings.traffic_schedule`, типово `DEFAULT_TRAFFIC_SCHEDULE` — розклад користувача: 104 цикли на добу без тривоги, 162 з тривогою. Його можна перевизначити в `[traffic.<провайдер>.schedule]`.
  - Вікно без `interval` означає «не опитувати»: `interval_at()` повертає None. Цикл опитування тоді чекає до `schedule.next_boundary()` або до зміни стану тривоги. Розклад, який не опитує ніколи, валідатор відхиляє — для цього є `enabled = false`.
  - Google у `config.toml` користувача: лише під час тривоги, 08:00–20:00, кожні 30 хв (≤ ≈ 8 900 запитів на місяць). Зразок — у `config.example.toml`.
  - Твердження про затор діє 3 найдовші інтервали на момент опитування (без урахування призупинених режимів).
- **`models.py`.** `Claim` стосується одного мосту й виду транспорту, але може охоплювати кілька напрямків. Має `status` (open/restricted/closed) і/або `congestion` — завантаженість, окремий вимір. `unknown` лише обчислюється, твердження його не стверджує.
- **`state.py`** — чисті функції без I/O, правила описані в docstring модуля. Ці правила ухвалено попередньо, користувач може їх змінити.
  - Твердження діє до `valid_until`, або до відбою (`until_alert_end`), або протягом `stale_after`/`stale_after_alert`.
  - Офіційне джерело переважає неофіційне, серед однакових перемагає новіше.
  - Якщо чинних тверджень немає, статус `unknown`.

## Конфіг і секрети (`config.py`)

- Пріоритет джерел: змінні `BM_*` → `.env` → файли секретів → `config.toml`.
- Секрети зберігаються лише поза `config.toml`. Локально — у `.env` (зразок `.env.example`). На сервері — Docker secrets: файл на кожну змінну в `/run/secrets/<ІМ'Я_ЗМІННОЇ>`, каталог змінюється через `BM_SECRETS_DIR`. Файли секретів читає `SecretFilesSource`, бо вбудований `SecretsSettingsSource` не розбирає вкладені ключі `__`.
- Токени мають тип `SecretStr`. Усі моделі конфігу мають `hide_input_in_errors=True`, інакше `ValidationError` показав би сирі токени. Нові моделі з секретами мають робити так само.
- Друкарська помилка в імені змінної з префіксом `BM_` у `.env` дає помилку валідації, а у звичайних змінних середовища тихо ігнорується.
- `tests/conftest.py` ізолює кожен тест від справжніх `.env`, `config.toml`, `/run/secrets` і змінних `BM_*`. Фікстура не діє під час імпорту модулів, тому не створюй `Settings()` на рівні модуля тесту: використовуй підклас лише з `init_settings`, як у `test_state.py`.
- Зразок несекретних налаштувань — `config.example.toml`.

## Версії продукту

Кодова база одна, версія перемикається в конфігураційному файлі.

| Версія | Джерела | Модерація людиною |
|---|---|---|
| Базова | лише офіційні | вмикається в конфігу (за потреби) |
| Розширена | офіційні + неофіційні | увімкнена завжди, вимкнути не можна |

Інваріанти забезпечено кодом:
- `accepts_source()` відкидає неофіційні джерела в базовій версії навіть для схвалених тверджень.
- Валідатори `Settings` не дають у базовій версії ввімкнути неофіційні джерела тривог чи заторів, а в розширеній — вимкнути модерацію.
- Провайдер заторів за замовчуванням неофіційний. Користувач може позначити його `kind = "official"`.

Чи публікувати розширену версію, користувач вирішить пізніше. Не закладай припущень щодо цього.

Застосовується законодавство воєнного стану щодо публікації інформації про критичну інфраструктуру, тож обережно з усім, що стосується автоматичної публікації. Перед публікацією похідних від Google даних треба перевірити умови Google Maps Platform.

## Технології (попередньо, ще не остаточно)

- Python 3.14, інтерпретатор встановлюється через pyenv. Менеджер пакетів: uv.
- aiogram для Telegram.
- Docker.
- Нереляційна (NoSQL) база даних, конкретну ще не обрано.

Сумісність із Python 3.14 (перевірено встановленням та імпортом на 3.14.8 у жовтні 2026):
- Для MongoDB бери асинхронний API самого PyMongo (`AsyncMongoClient`). Motor застарів. Beanie 2.2 декларує `Requires-Python <3.14`, тож `uv add` його не встановить.
- Pyrogram покинутий (останній реліз 2023). Якщо потрібен Telegram-клієнт для читання каналів, бери Telethon або форк Kurigram.
- У selectolax 1.0 старий бекенд `selectolax.parser` прибрано, використовуй `selectolax.lexbor`.
